# WMS 2.0 Rewrite Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild WMS Pallet Tag System 2.0 as a workflow-centered modular application while preserving proven label, barcode, rail, queue, resume, config, update, packaging, and smoke behavior.

**Architecture:** Use Clean Architecture / Ports and Adapters. Domain and application use cases become independent of Oracle, UI, Picocli, filesystem, and printers; CLI and desktop become adapters over shared workflows. Analyzer tools and SSCC-specific ZPL tooling are intentionally not ported.

**Tech Stack:** Java 21 preferred for 2.0, Maven multi-module, JUnit 5, HikariCP, Oracle JDBC, Picocli, JavaFX preferred for desktop, existing ZPL/PDF rendering dependencies as needed.

---

## File Structure Target

Create these modules:

- `wms-domain`: pure domain models and rules.
- `wms-application`: use cases, ports, workflow DTOs, typed errors.
- `wms-oracle`: Oracle repositories and row mappers.
- `wms-printing`: ZPL/PDF rendering, printer routing, print dispatch.
- `wms-files`: config, runtime settings, artifact store, checkpoint file store.
- `wms-cli`: Picocli commands over application use cases.
- `wms-desktop`: desktop shell and workflow screens.
- `wms-smoke`: repo/package smoke scenario harness.

Keep existing `core`, `db`, `gui`, and `cli` modules temporarily during migration. Do not delete old modules until replacement workflows are proven.

Use `com.tbg.wms.v2.*` packages in the new modules while old modules remain in the reactor. This prevents split-package confusion with existing `com.tbg.wms.cli`, `com.tbg.wms.core`, `com.tbg.wms.db`, and GUI classes during the parallel migration.

## Execution Rules

- Follow TDD for every production change.
- Keep old and new implementations side by side until parity tests pass.
- Prefer immutable workflow DTOs.
- Do not port analyzers.
- Do not port SSCC-specific ZPL tooling.
- Keep barcode generation and related tooling.
- Commit after each task if this is being executed on a real branch.
